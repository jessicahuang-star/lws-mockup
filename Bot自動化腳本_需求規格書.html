01功能總覽與定位

為每一隻 Bot 提供「事件觸發 → 後續自動化動作」的能力，擴充目前僅有單一事件訊息的現況。

功能名稱Bot 自動化腳本
目的讓後台管理者（HR）針對成員相關事件，設定延遲、多對象、可等待使用者回應的自動化訊息流程。
Bot 定位內部通知型
可套用範圍每一隻 Bot 皆可設定
功能位置Bot 管理 → 5.1 BOT管理設定 → 編輯 → 自動化服務（與「基本設定」「互動設計」同層並列，詳見 §11.0）
核心概念預設訊息負責「即時單則」；自動化腳本負責「有選擇（對象／時間／流程）的後續行為」。

02功能架構（兩入口分界）

兩入口功能獨立（各自可單獨設定），但 UX 上刻意相連：自動化是預設訊息的「升級路徑」。

預設訊息

互動設定｜即時單則・入門
  • 對象：依事件固定、不給選（當事人／群組，見 §03）
  • 時間：固定立即
  • 內容：單一則
升級 →
需要選對象／延遲／等回應

自動化腳本

Bot 設定｜延伸流程・進階
  • 對象：可選（本人／主管／管理者，複選）
  • 時間：只走延遲（10 分鐘～最大 30 天，無立即）
  • 流程：A 型 / B 型、可等完成
判準：要延遲、選對象、或等回應 → 用自動化腳本；發生當下就發一則給當事人 → 用預設訊息。
時間分工：預設訊息＝立即（唯一）；自動化＝只走延遲（10 分鐘起，最大 30 天）。兩者不重疊。
對象分工：預設訊息＝只發給事件的直接關係人（當事人／群組）；主管與 Bot 管理者一律走自動化。兩者不重疊。

兩者共用同一份事件字典（同名）；重疊是刻意的，靠能力差異自然分流，並以「從預設訊息一鍵延伸成自動化」避免混淆。

04兩型流程（A 型 / B 型）

A 型與 B 型唯一差別：要不要加一個「中間條件」讓使用者操作（＝等完成）。兩者都能設彈性延遲。

注意：「A 型／B 型」為本文件的內部術語，不得出現在使用者介面。介面上以卡片裡有沒有 postback 類訊息區塊（按鈕／輪播圖）表達此差異——
・卡片不含按鈕／輪播圖 → 直接接結束（＝A 型）　・卡片含按鈕／輪播圖 → 必須再接「時間 → 卡片」（＝B 型）

07訊息的優先級定義

一則互動進來，先看它是哪一種 callback 事件（Postback 或 Message），再走對應規則。兩者是不同事件類型，處理路徑分開。

🅐 Postback 事件（按了帶 postback 的按鈕）

直接依按鈕資料處理；若這顆是某 B 型的完成鈕（卡片常駐按鈕 ＋ postback）→ 推進流程。結束。
postback 不經過關鍵字／fallback 比對，路徑最單純。本規格完成訊號採此路。

🅑 Message 事件（送出文字，含關鍵字、快速回覆送文字）— 依序比對

  1. 真人服務關鍵字（全站統一控制）→ 轉真人。最高，可中斷進行中的流程。
  2. B 型完成監聽（僅當完成訊號改採「文字」時才會用到）→ 被流程吃掉，推進（不再跑關鍵字、不進 fallback）。
  3. 一般關鍵字 → 關鍵字回覆。
  4. 自動回覆（fallback） → 都沒命中，最後才回。
鐵則：被「完成監聽」吃掉的訊息，絕不可再進「自動回覆」。真人服務關鍵字＝保留字，任何 Bot 的關鍵字／完成訊號都不得使用（用了會被劫走），設定時應擋掉或警告。
因本規格完成訊號採 postback（走 🅐 路），🅑 的「完成監聽」在此設計下用不到——僅退回文字方案時才需要。

B 型「等待完成」中 × 各種訊息進來 — 行為對照表

使用者做的事走哪條路 / 反應B 型流程狀態

09已知限制（MVP）

不做逾時「提醒」分支（Lv3）：B 型若使用者一直不完成，滿 30 天由時效期限自動作廢（Lv1），但不主動提醒 HR（無人知道誰沒完成）。
沒有「立即」：自動化最短延遲 10 分鐘（§05），通報類訊息（如成員移出群組通知主管）必然有至少 10 分鐘落差。此為刻意取捨——「立即」屬預設訊息的能力範圍。
重複觸發會取消舊流程：同一成員同一流程再次觸發時，以最新事件為準、取消舊流程（Q-P01 決議）。使用者手上舊卡片的「我已完成」按鈕按下後不會有任何反應（常駐按鈕無法收回，系統靜默忽略）。
無節流機制：大量組織異動（如月初批次匯入 200 名新成員）會在同一時刻產生大量推播，人工停用來不及。MVP 僅有發送端速率控制（技術自保），實際送達時間可能晚於設定值。詳見 §11.5。
不做靜音時段：延遲若落在深夜或假日照樣發送。未來可補「僅在服務時段發送」。
組織事件僅在「SaaS 後台操作路徑」才會觸發：變更若發生在 LINE WORKS Admin 端或定期同步路徑，事件不會觸發，將造成部分員工收到通知、部分沒收到。MVP 不做補償機制，導入時需與 HR 約定「組織異動一律於 SaaS 後台操作」（見 §11.5 Q-B04）。
同一次人事作業可能產生多則通知：部門＋職位同時異動、先建檔後補部門、新增成員後又加入 Bot 群組 —— 當事人會收到 2 則。MVP 不做合併／抑制，各則文案須能獨立成立。
管理者／主管的通知一定慢於當事人：這兩種對象只能走自動化，最短延遲 10 分鐘，且會佔用「每隻 Bot 5 條流程」額度；三個組織事件都要通知管理者將佔掉 3 條。
流程長度上限：一條流程最多 2 張卡片（即 初始設定 → 時間 → 卡片 → 時間 → 卡片 → 結束），不做更深的串鏈、不做分支與條件判斷。
一事件一流程：每個起始事件只能建立一條自動化流程，已被使用的事件不會出現在其他流程的選項中。上限為每隻 Bot 各 5 條（＝ 5 個事件各一條）。同一事件的多段訊息請用同一條流程的兩張卡片表達。
連帶限制：組織層事件（新增成員／部門異動／職位異動）在多隻 Bot 各自設定時會對同一位員工重複發送內容相同的訊息，系統不阻止（人為設定失誤，MVP 先忽略）。

11.1架構分層與資料流

建議切成五層，各層失敗互不污染，並讓「觸發」與「發送」之間一定隔一層可持久化的排程佇列。

① 觸發層（Trigger）後端

兩種來源：組織事件（後台改部門／職位／新增成員 → Laravel Event / Model Observer）與 群組事件（LINE WORKS webhook callback → 既有 BotWebhookController）。職責僅止於：辨識事件 → 找出對應流程 → 建立執行實例。

② 實例層（Run）後端

每個「事件 × 當事人」開一筆 run，鎖定當下的流程版本與變數快照（姓名、新舊部門…）。run 是唯一有生命週期的東西，狀態機見 §11.4。

③ 排程層（Schedule）後端

每個待發卡片寫一筆 job（含 scheduled_at）到資料表，由排程器每分鐘掃描到期項目丟進 queue。不使用 queue 的 delay 直接排 30 天——理由見下方 callout。

④ 發送層（Dispatch）後端

解析收件人 → 組裝訊息 payload → 呼叫 Send API → 記錄結果、重試、速率控制。

⑤ 監聽層（Listen）後端

webhook 收到 postback → 用 token 找回 run → 冪等地推進流程。必須與既有關鍵字／fallback 的優先序共存（§07）。

為什麼排程不能只用 queue delay：Redis 的 delayed job 排 30 天有三個現實問題——① Redis 資料若非持久化或做過 flush，等待中的流程整批消失且無跡可查；② 要「取消」某條等待中的流程（停用流程、真人服務接手）時，delayed job 難以精準撤回；③ 部署時的 queue restart 與版本不相容風險累積 30 天。
建議：DB 表當作真實來源，queue 只負責「現在該發的那一批」，是可觀測、可取消、可重跑的做法，也讓未來「等待中名單」功能免費取得。

機制建議做法
掃描排程器每分鐘撈 state=pending AND scheduled_at <= now()，以 SELECT … FOR UPDATE SKIP LOCKED 或原子性 update state=dispatched 領取，避免多台 worker 重複發送（Q-B08）。需有 batch size 上限，見 §11.5。

速率控制發送 worker 需限流（見 §11.5），建議 Redis token bucket，per tenant / per bot 各一層。
清理建議 90 天後歸檔或刪除，避免無上限成長（Q-P08）。

11.4執行語意與異常路徑

§01~§10 描述了「會發生什麼」，這一節補齊「異常時的行為」。

run 狀態機

狀態進入條件離開條件

→ cancelled / failed

情境處理方式

與真人服務、關鍵字的互斥關係

好消息：因完成訊號採 postback（§06 定案），它走的是與關鍵字／fallback 不同的 callback 事件類型，兩者天生不衝突。webhook 分派邏輯：先看是不是 postback → 是則查 token → 命中則推進並結束處理；不是 postback 才進既有的關鍵字／fallback 流程。既有行為完全不受影響。
已決議與真人服務的交集（Q-P14）：發卡片時若該成員正處於真人服務中（查 bot_conversation_states 或 human_service_conversations.state IN (pending,serving)）——
・B 型「等待完成」中遇真人接手 → 取消該 run（狀態轉 cancelled）。B 型的前提是「人在且會回應」，真人接手代表對話情境已變，繼續等待無意義。
・A 型 → 照發，不檢查真人服務狀態。A 型是單向通知，與真人對話無關。
不實作「延後至服務結束」（需額外的排程重掛機制，成本較高）。

批次觸發的風險

§11.0 已察覺「人工停用擋不住瞬間大量觸發」，但實際規模更大。典型情境：月初 HR 一次匯入 200 位新成員。
量體分兩層看：
・預設訊息：200 位當事人 × 各 1 則 = 200 則、且為「立即」發送（無 10 分鐘延遲可當緩衝）。
・自動化：200 個 run，若對象複選了主管與管理者，10 分鐘後同一時刻再發 200~600 則。
三個必須處理的點：
① Send API 速率限制（Q-L03）—— 需查證 per bot / per tenant 的配額。超限會整批失敗；預設訊息那 200 則沒有延遲可以攤平，更為吃緊。
② 排程器單次撈取量 —— 必須有 batch size 上限，否則一次撈 600 筆同步發送會拖垮 worker。
③ 訊息品質 —— 對象改為當事人後，預設訊息不再有洗版問題（每人只收自己那一則），故不需要彙整或去重機制、工程請勿為預設訊息實作彙整邏輯；洗版風險只剩自動化選了主管／管理者時（少數人收到大量通知）。
即使 MVP 不做「熔斷」，也必須做發送端限流（technical safeguard，不是功能）：per bot 每秒 N 則、超出的自然延後。注意：此限流會使預設訊息的「立即」在批次情境下實際變成數分鐘內陸續送達——「立即」應理解為「儘速、不排隊等待設定時間」。自動化側已寫入 §05「不早於設定時間」。
